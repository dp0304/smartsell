# 商品上架核对与目录导入

Codex or Claude drives the workflow in the requested workspace's connected SmartSell MCP. Inspect the live tool list and schemas or use `smartsell_operations_describe`. Prefer named tools. Use `smartsell_operation_call` only for operations the current credential is allowed to call and the live catalog describes. Resolve names from authorized context before asking for IDs. Keep the requested workspace, store, account and device fixed. The Agent handles calls and readback without asking the user to claim desktop tasks, copy session IDs or run commands.

1. **Locate and check.** Use `workspace_get_context`, `commerce_store_list`, `catalog_search` and `catalog_get_product` as exposed. For listing, confirm the exact product, variant, SKU, catalog fields, store provider and external store ID. Compare any current verified Chrome identity evidence against the requested store, device and session. Treat a binding as routing information and report when Chrome identity is unverified. Ask only about unresolved matches or actual authorization, login or review gaps.
2. **Import when requested.** Read `worker_catalog_list` to match the store and its fixed Worker. If the requested device matches the binding and the operation is available, call `worker_catalog_request_import` with `params: { id: STORE_ID }`, `body: {}` and an `idempotency_key`. Do not rebind or pick another device. Read the same job ID in `worker_catalog_list`, and use `import_get` and `import_rows` for its `import_id` when exposed. Report the actual status and error, row preview or merge counts. If the requested listing depends on this import, wait for the import and resolve the SKU again before handling the listing request. Reuse the key only for identical retries. `queued`, `claimed` and `previewed` are distinct from `imported`. If the existing Worker path requires an operator to verify the merchant, provide the export or confirm the preview, identify the exact pending step on the bound Worker or in Workbench. Creating an import task neither imports the file immediately nor requests a marketplace listing.
3. **Handle an explicit listing request.** Current SmartSell has no marketplace listing executor. When both receipt operations are available, call `desktop_request_capability` with `body: { capability: "product_listing", product_id, variant_id, store_id }` using the validated catalog references and a separate `idempotency_key`. Then call `desktop_get_capability_request` with `params: { id: REQUEST_ID }`, or use it directly for an existing receipt. Report the same ID and returned status and reason (`unsupported` / `product_listing_not_supported` in the current implementation). If either operation or a required reference is unavailable, report the gap and any confirmed ID. Never substitute a catalog edit, imported file or recorded listing for a marketplace write.
4. **Report and close the loop.** Summarize the store, SKU, device, confirmed action, job or receipt ID and blocker. When handling an existing Agent job leased to this client, read `agent_jobs_get` and use the latest `expected_version` and this claim's `fencing_token`. If authorized, use `agent_jobs_submit_result` with `result_ref: { note: ... }` only for a requested readiness output that accepts a note. For actual listing or a blocked job, use `agent_jobs_handoff` with `done_summary` and real `pending_side_effects` (empty if none). Report the result of the call. Do not create or claim a job just to record the outcome, borrow another lease, or use shell, HTTP or platform tools to bypass a missing operation.
