# 数据采集与核对

## 自己的社媒账号状态与近期作品

For “查我的社媒状态” and “我的 X 账号现有视频”, use only the authorized SmartSell MCP and the user's own paired Worker. Check the live schemas for `worker_social_status_request` and `worker_social_status_get`.

1. Queue `worker_social_status_request` with a fresh high-entropy random `idempotency_key` (such as a UUID v4) for each new user query, even for the same brand and day. You may use local `uuidgen` solely to generate the ID, without network access. Never derive the key from a brand, date, or fixed sequence. Reuse the exact key and arguments only for a network retry of the same submission. In `body`, use `mode: "account_status"` for account or login state and `mode: "recent_posts"` with `platform: "x"` for existing X videos or recent posts. Recent posts currently support X only. For account status, set `platform` when specified. Omit `device_id` when the user has exactly one eligible paired Worker. If multiple Workers match, resolve the intended device from authorized context or ask for it. Include `expected_identity` only when the requested identity is known. Use the handle for X.
2. Poll `worker_social_status_get` with `params: { id: TASK_ID }` for the same task. Report the task ID, device ID, observed state for each platform and the Worker receipt time (`reported_at`). For an X video query, return links only for posts with `has_video: true`. Label a task from an earlier query, including a replay of that task, as a historical receipt with its original observation time. If still queued or claimed, report that state and the absence of an observation. If blocked, report the exact code and reason, such as unavailable tools or permissions, no paired Worker, a device offline, login or verification required, identity mismatch, expiry, or unsupported collection. Tell the user which Worker needs attention when applicable. Any requested sign-in belongs in visible Chrome on that Worker.
3. Keep the live check on the Worker. Do not fall back to external tools, the main Agent's local browser, web search, shell, curl, proxies or scraping. Label any stored posts or metrics as cached workspace data, with their original time and coverage when available. Missing or partial observations cannot establish a count of zero or prove an item is absent. For a specific existing SmartSell schedule, use the publishing target and its linked receipt to establish publication. A recent-posts observation establishes only what that Worker saw.

## 其他采集任务

Use the connected SmartSell MCP for the selected workspace. For the chosen action, check the live MCP tool inventory (or `smartsell_operations_describe`) and advertised input schema. Ask for missing subject IDs, time range, metrics, or sources rather than guessing. A tool being discoverable does not grant access to the platform data.

- **query**: If permitted, call `metrics_query` for the named subjects and time range. Report coverage, evidence, timestamps, and warnings. Keep `no_permission` and missing observations distinct from a measured zero. Do not present estimates as observations or claim these numbers were just collected from a platform.
- **record**: Use `analytics_record_observations` only if it is exposed and allowed, the operator supplied the observations from a source they are allowed to use, and the user explicitly confirmed recording them. Preserve provenance and observation time; include only the requested, allowed metrics. Follow the current schema and the service's idempotency requirements. Report what the service actually accepted, not merely what was supplied.

- **zhihu-login / zhihu-stats**: Only when `zhihu_stats_create` and `zhihu_stats_get` are available to this credential, use their advertised schemas. Ask for the user's own paired Worker ID if unknown; use `mode: login_check` alone for preflight, or the slug of the user's own Zhihu profile for stats. Send an idempotency key when queuing. Read back the issued task ID through SmartSell and distinguish `queued` and `claimed` from a reported result. Only a successful identity-checked statistics result is evidence of observed counts. On `login_required`, ask the user to sign in in visible Chrome on that Worker and point to Web → Agent → Zhihu Worker incidents. Do not fill credentials, bypass identity checks, scrape from the terminal, or invent metrics. Do not requeue automatically when blocked.

For Workspace-only reads, do not ask the operator to reverify Chrome. If the task concerns a specific external account or store and the authorized context exposes current verified Chrome proof, compare the platform, device/session and identity with the requested subject and report the match or mismatch. A linked account, an open page, and the presence of platform metrics are not Chrome identity evidence. If proof is not exposed, label it unverified here; don't acquire it through an unauthorized path.

If data or access is unavailable, report the gap with whatever checks succeeded. Ask the operator to step in only for missing required permission, external login/verification, or an existing approval gate (ask for an identifier only if it cannot be resolved from authorized context). Do not scrape, launch an unsupported Worker task, log into third-party sites, read credentials, or switch to HTTP, shell, or generic tools to get around missing access.
