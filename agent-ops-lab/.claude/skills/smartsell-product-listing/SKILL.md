# 商品上架准备

This preset verifies readiness. It cannot create an approval, Worker job, or marketplace listing. Explain this boundary up front; recording an unsupported request is not submitting a listing.

1. Ask for the SmartSell workspace and the existing product and store identifiers if missing or ambiguous. Use its connected SmartSell MCP only. Inspect the live tool inventory (or `smartsell_operations_describe`) and advertised schemas for `catalog_get_product` and `commerce_store_list`. If unavailable or denied, report the blocker and direct the user to the Workbench product and store views. Do not substitute a generic write, HTTP, shell, or platform API.
2. Read the product and locate the store. Review the matching variant, SKU and catalog fields. If the authorized context already contains a current verified Chrome store identity, compare it with the expected platform, device/session and external store ID; report whether they match. A binding, record, or open admin page alone proves neither identity nor write permission. If the current MCP does not expose the Chrome proof, report it as not verified here; do not ask the operator to repeat a check already proven. Flag only unresolved permissions, identity/login, or approval gates.
3. Report that the current SmartSell tools cannot perform marketplace listing; preparation does not equal listing. Do not modify the catalog or record an observation as if a listing existed. When the user explicitly asks to list and the connected MCP advertises `desktop_request_capability` and `desktop_get_capability_request`, use their live schemas to record and read back the `product_listing` receipt with the validated references and an idempotency key. Report its ID and actual `unsupported` reason; if unavailable or denied, do not claim a receipt exists or substitute a different write. For an existing Agent job already leased to this client, leave a trace using only advertised, authorized job operations: read `agent_jobs_get` for the current version and expected output, then use `agent_jobs_submit_result` with `result_ref: { note: ... }` only for a requested readiness report whose output accepts a note. If the job requested actual listing or is blocked for human action, use `agent_jobs_handoff` with `done_summary` and any real `pending_side_effects` (empty when there were none). Include the job ID, current `expected_version` and the `fencing_token` from this client's claim; don't reuse someone else's lease or guess a token. Summarize checks, blockers and that no platform write occurred. If no such owned lease or tool is available, don't create or claim a job just to log the outcome. Don't claim a handoff succeeded if it failed.
