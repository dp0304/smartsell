# S5（媒體路徑）對其他工作流的請求

S5 owns `packages/agent-relay/**`, `packages/media-store/**`, `apps/server/src/integration/agent-uploads.ts`, `apps/server/src/integration/media-host.ts`, `apps/server/src/extensions/media-files.ts`. Everything below is a change in a file S5 does not own, or a contract other streams consume. Each item names the file, the function, the change and why.

## S4 (MCP and agent credentials)

1. **`apps/server/src/integration/command-mcp.ts`, after `/mcp` is registered (C5, §6.4 「註冊」):**

   ```ts
   import { registerAgentUploads } from './agent-uploads.js';
   registerAgentUploads(app, { credentials, media: operationApi.media.media, config: operationApi.config });
   ```

   Until this call exists the upload routes (`/api/v1/agent/uploads*`, `GET /agent/relay.mjs`) are not mounted on the real hub; every S5 test mounts them on its own Fastify instance. `media` is `createMediaHost(config).media` (it now exposes `.storage` and `.maxBytes`). `config` needs `mediaDirectory` and `maxUploadBytes` (S1 has added both). The return value has `idle()` (resolves when no assembly runs) for graceful shutdown; optional.
2. **C4 principal (`integration/agent-credential.ts`):** S5 codes against a structural copy (`UploadPrincipal`, `UploadCredentialService` in `agent-uploads.ts`). Requirements S5 relies on:
   - `authenticate(req)` returns `undefined` (not a throw) for a missing, revoked or expired `Bearer ss_command_…`; S5 answers 401 `UNAUTHENTICATED` with `WWW-Authenticate: Bearer` (a thrown `DomainError` with status 401 is also accepted).
   - `run(true, fn)` must wrap the work in `unit.command({ module, action, key: 'internal/<uuid>', fingerprint: '' }, …)` and `flush()` the Operation records, exactly like `mountCompatibleMedia` in `media-host.ts`; the memory and local stores refuse writes outside a command ("Writes require an active command"). The S5 test fixture `packages/agent-relay/test/fixtures/hub.ts` is a working reference.
   - `run(write, fn)` may be called after the HTTP request ended: the background assembly (§6.4 step 3) reuses the principal of the `complete` request for its two short writes.
   - S5 additionally checks `WRITE.includes(ctx.role)` inside every transaction.
3. **`media_upload` on the hub (`mcp-hub-tools.ts`, §6.3 「其他」):** the hub tool must answer `RELAY_REQUIRED`. S5 did **not** add a one-time `PUT` URL endpoint for `details.upload_url_flow`: no such route is in Appendix B, and a whole-file PUT would hit the 8 MiB part limit and the 120 s request timeout. Until the lead decides, give `details` the relay install commands (`curl -fsSL https://<hub>/agent/relay.mjs -o ~/.smartsell/relay.mjs` and the `codex mcp add …` line from §6.2 item 6) and no URL. Do not return a success-shaped value.
4. **Output schema of `media_upload` (§7.2.5):** the relay's `structuredContent` has exactly these 15 keys: `media_id, status, filename, kind, mime, bytes, sha256, uploaded_bytes, eta_seconds, continues_in_background, duration_ms, width, height, deduplicated, web_url` (`duration_ms`/`width`/`height` may be `null`, `web_url` is always `null`). If the hub's `outputSchema` is strict, keep it to these. When `status` is not `ready` the result carries a second `content` block (plain English note for the model: keep the computer awake / do not close the conversation); `content[0].text` is always the same JSON as `structuredContent`.
5. **Instructions (§7.5):** the relay's `PATH_NOT_ABSOLUTE` message is exactly "Pass an absolute path. Build it from your working directory; the relay does not know it."

## S1 (hub runtime)

6. **Relay bundle on the hub:** `GET /agent/relay.mjs` serves `packages/agent-relay/dist/smartsell-relay.mjs`; when it has not been built the route answers 503 `RELAY_BUNDLE_MISSING` (with a zh-Hant `details.owner_message`). Please run `pnpm --filter @smartsell/agent-relay build` in `hub:init`, `hub:update` and `install-hub` (the root `pnpm build` already does it through turbo, the package has a `build` script). The build has no dependencies of its own: it borrows the pinned `esbuild` of `apps/connector-desktop` (see `packages/agent-relay/scripts/build.mjs`).
7. `createMediaHost(config)` now reads `config.mediaDirectory` and `config.maxUploadBytes` (§6.5, §6.7); `mediaStorageFromEnv` no longer reads `NODE_ENV`. The `process.env.MEDIA_DIRECTORY ??= config.mediaDirectory` bridge in `hub/startup.ts` and the `media-files.ts` entry in the `hub.test.ts` NODE_ENV audit list can be removed (harmless if kept).
8. The `files.cleanup` schedule from `createMediaHost` now also fails agent upload sessions older than 24 h (hourly per workspace). Nothing to wire: `bootstrap.ts` already schedules `media.schedule`.

## S2 (precheck, content)

9. **Upload states S2 reads (§3.8, §4.4):** while uploading, `asset.status ∈ {uploading, processing}`, `asset.ownership='owned'`, `asset.origin='agent_upload'`, `asset.brand_id=null`, and `asset_version.file_object_id=null` with the declared `sha256`/`mime_type`. At completion, in one short transaction, `asset_version.file_object_id`, `mime_type` (corrected from the bytes) and `meta` (`{duration_ms, width, height, codec, has_audio}` or `null`) are written, `asset.status='ready'`, and `asset.version.created { asset_id, asset_version_id, version_no: 1, source: 'agent_upload' }` plus `asset.asset.ready` are emitted. A failed upload sets `asset.status='failed'` and `asset.failure = {code, message}`.
10. **No metadata:** `asset_version.meta === null` when ffprobe is missing (`file_object.probe_status='unavailable'`) or could not read the container (`'invalid'`); the asset is still `ready` (bytes are SHA-256 verified). This is where the risk 「未取得影片長度與尺寸」 applies.
11. **`apps/server/src/modules/content/revisions.ts` `staleEvents['asset.version.created']`:** it marks content that references the asset as `asset_updated`/stale. For `source: 'agent_upload'` the first version's bytes arriving is not a content change; please skip those events, otherwise every post scheduled while its video was uploading would go stale when the upload finishes.

## S3 (Worker job engine)

12. **Signed device download (§6.6):** in the GET handler, after the short read-only transaction, call
    `openMediaRange(media.storage, { storage_key: file.storage_key, byte_size: file.size_bytes }, range)` and stream `.stream`; parse the header with `parseByteRange(request.headers.range, size)` (both exported from `extensions/media-files.ts`; 416 `RANGE_NOT_SATISFIABLE` carries `details.size`). `ETag` is `"<file.sha256>"`.
13. `payload.media[].file_id` = `asset_version.file_object_id` once the upload is ready (`null` while uploading). Use `asset.version.created` with `source: 'agent_upload'` (or `media.upload.ready { upload_id, media_id, file_object_id }`) to clear `media_pending`; `mediaUploadProgress(ctx, mediaId)` (from `agent-uploads.ts`) gives `{status, bytes, bytes_received}` for `JobMedia`/views.
14. If you add an `application/octet-stream` parser for `PUT /api/v1/device/evidence/:job_id`, register it inside an encapsulated plugin (as `agent-uploads.ts` and `media-files.ts` do); a root-level parser for the same type makes the sibling registrations throw `FST_ERR_CTP_ALREADY_PRESENT`.

## S7 (web and read models)

15. Post page upload progress (§6.3 step 9): `mediaUploadProgress(ctx, mediaId)` → `{ upload_id, status, bytes, bytes_received, error, expires_at } | undefined` (latest session for that media). Sessions live in the Operation kind `media_upload_session`.

## S9 (Worker App)

16. **Relay mode (`--mcp-relay`, §6.2):** add `"@smartsell/agent-relay": "workspace:*"` to `apps/connector-desktop/package.json` (the workspace package is linked; it has no dependencies) and call
    `relayMain({ argv: process.argv.slice(1), stdin: process.stdin, stdout: process.stdout, stderr: process.stderr, defaultConfigPath: join(app.getPath('userData'), 'agent-relay', 'config.json') })` → exit code. `--mcp-relay` itself is accepted and ignored by the parser. The credential file next to `config.json` must be `0600` and owned by the user (checked on macOS/Linux).
17. **Upload handoff (C12):** listen with `createHandoffServer(handoffSocketPath(<userData>/agent-relay), accept)` (macOS: `<dir>/ipc.sock`; Windows: `\\.\pipe\smartsell-agent-<user>`). Message: one JSON line `{type:'handoff', upload_id, path, sha256, bytes, mtime_ms}` (strictly validated by `isHandoffMessage`), reply `{ok:true|false}`. In `accept`, start `continueUpload({ hubOrigin, token, uploadId, path, sha256, bytes, mtimeMs, onProgress, signal })` and return `true`; answer `true` again (without a second upload) when you already run that `upload_id` — a relay that resumes an upload asks the App first. `continueUpload` throws `UPLOAD_SESSION_MISMATCH` when the hub session's SHA-256/size differ (refuse), returns `{status:'failed', error:'FILE_CHANGED'}` after telling the hub to abort, and retries for 30 minutes through hub restarts. Hold the idle-sleep blocker while it runs.
18. **Windows Node relay:** copy `packages/agent-relay/dist/smartsell-relay.mjs` (or `GET /agent/relay.mjs`) to `<userData>\agent-relay\smartsell-relay.mjs`; client config `command = "node"`, `args = ["<that path>", "--config", "<userData>\\agent-relay\\config.json"]`.

## S10 (owner alerts)

19. Done as requested: S5 calls `alertUploadFailed(ctx, { media_id, filename, reason })` in the transaction that marks the upload failed, with `reason` ∈ `file_changed | cancelled | error | expired | UPLOAD_HASH_MISMATCH`. `upload_done` is left to your `asset.version.created` trigger (S5 sets `origin='agent_upload'` and `status='ready'` before emitting). S5 also emits `media.upload.started|ready|failed` (`ready` has `background: true` when it finished more than 50 s after creation) if you want them.

## Lead (Appendix C)

20. Codes S5 returns that Appendix C does not list (please add or rename): `UPLOAD_INCOMPLETE` (409, complete before every chunk arrived; `details.missing`), `UPLOAD_NOT_RECEIVING` (409, a part after complete), `UPLOAD_ALREADY_READY` (409, abort after ready), `UPLOAD_LIMIT` (429, 32 uploads in flight), `RELAY_BUNDLE_MISSING` (503), `UNAUTHENTICATED` (401), `PERMISSION_DENIED` (403), `LENGTH_REQUIRED` (411), `UNSUPPORTED_MEDIA_TYPE` (415), relay-side `HUB_UNREACHABLE`, and `continueUpload`'s `UPLOAD_SESSION_MISMATCH`. `MEDIA_NOT_FOUND` is reused for a missing local file and an unknown `upload_id`.
21. Decision to confirm: when ffprobe exists but cannot read the container, S5 records the asset as `ready` with `meta=null` (same as a missing ffprobe, §6.5) instead of failing it; E2E-11 allows an "mp4 header plus mdat filler" file, which ffprobe cannot parse.
