# S4 (posting API and MCP): requests to other workstreams

S4 owns `apps/server/src/modules/posting/**`, `apps/server/src/integration/{command-mcp,agent-connections,agent-credential,mcp-hub-tools,mcp-hub-instructions}.ts`, `apps/server/src/extensions/{mcp-streamable,mcp-tools}.ts` and (E8) `apps/server/src/modules/content/revisions.ts`. Everything below is a change in a file S4 does not own, or a contract other streams code against. Each item names the file, the function, the change and why.

## What S4 provides

- **C4** `integration/agent-credential.ts`: `createAgentCredentials({ store, codec, operations })` → `AgentCredentialService`. `authenticate(req)` returns `undefined` (never throws a 4xx) for a missing, malformed, revoked or expired `Bearer ss_command_…`, and only for agent connections (`kind === 'agent_connection'`, write access). `principal.run(write, fn)` re-checks the credential in every transaction (a connection revoked after `authenticate` stops background work too), checks `WRITE` for writes (403 `PERMISSION_DENIED`), wraps writes in `unit.command({ key: 'internal/<uuid>' })`, flushes the Operation records and bumps `stream/revision`. `ctx.agentCredentialId` is set, so `fromAgent(ctx)` is true inside it. It can be called after the HTTP request ended (S5 background assembly). `agentTokenCodec(secret)` seals/opens the tokens; `toolProfile(row)` reads `tool_profile`.
- **Mounts** (`command-mcp.ts`, after `/mcp`, only when the Operation API is configured): `registerAgentUploads(app, { credentials, media, config })` (S5) and `registerAgentAlertStream(app, { credentials })` (S10). `media` is `operationApi.media?.media ?? createMediaHost(config).media`; a `preClose` hook awaits `uploads.idle()`.
- **Operations** (module `posting`, full names, WRITE incl. Agent): `hub_posts_schedule` `POST /hub/posts/schedule`, `hub_posts_update` `POST /hub/posts/:id/update`, `hub_channels_check` `POST /hub/channels/:id/check`, `hub_publishing_pause` `POST /hub/pause`. Bodies are the strict zod schemas of `modules/posting/schemas.ts` (REST and MCP share them).
- **Subscriber** `posting.unblock` (exported from `modules/posting/index.ts`, picked up by `discoverOperations`).
- **Agent read models** `modules/posting/{posts,views}.ts`: `agentPost`, `listAgentPosts`, `postDetail`, `overview`, `machinesList`, `channelsList`, `taskDetail`; `configurePosting({ publicOrigin, webUrl })`.
- **`/agent-connections/redeem`** now also returns `id`, `connection_id`, `workspace_id`, `client`, `mcp_url` (additive) so the laptop App can write `config.json` (§6.2 step 3).

## S3 (Worker job engine)

1. **`createCheckLoginJob`** (C3, installed through S2's `setWorkerEngineHooks`): S4 calls it from `hub_posts_schedule` (login older than `LOGIN_CHECK_MAX_AGE_H`, same transaction) and from `hub_channels_check`. S4 first reuses an open `check_login` of the channel (any non-terminal status), so S3 may assume it is called only when none is open; please still reuse one if it is. Return the `worker_job` row (`WorkerJobRecord`). Without the hook, `post_schedule` still schedules and reports `warnings[].code = 'login_check_unavailable'`; `channel_check` returns your 503 `WORKER_ENGINE_UNAVAILABLE` as is.
2. **What the Agent reads from your records** (no import of `modules/worker`): `publish_target.worker_job_id` (else the newest `worker_job` with `publish_target_id` and `kind='publish_post'`), `worker_job.{status, revoke.reason, blocker, result, device_id, not_before, not_after, dry_run}`, and `worker_job_event.{job_id, at, event, detail.text | detail.message}` for the `post_get`/`task_get` timelines (newest 10 / 30). Please keep `target.worker_job_id` on the live job.
3. **Errors S4 passes through unchanged** from `planning.cancel()` → your Worker-aware `requestCancellation`: Problems with codes `POST_LOCKED` (409) and `POST_RESULT_UNKNOWN` (409). S4 also maps `LEASE_HELD` from `updateTarget` to `POST_LOCKED`. Please throw Problems whose `status`/`code` are set (S4 checks them by shape, not `instanceof`: the domain package's `Problem` is a different class instance from `@smartsell/contracts`).
4. FYI: `apps/server/src/hub/hub.test.ts` "audit: config.production call sites and direct NODE_ENV reads" currently fails on `apps/server/src/modules/worker/model.ts` (a direct `NODE_ENV` read). Not S4 code.

## S7 (Web and read models)

5. **C7 builders**: `modules/posting/views.ts` and `posts.ts` build the Agent projections from the records because `views/{today,machines,channels,posts}.ts` are not in the tree. When your builders land, either keep these (they use the same `derivePostStatus`, `channelLoginState`, `deviceOnline`) or have S4 compact `buildOverview`/`machineSummaries`/`channelSummaries`/`listPosts`/`postDetail`/`jobDetail` at integration. Do not register `views_*` names inside `posting` (S4 does not).
6. **`webUrl(ctx, kind, id)`**: register it with `configurePosting({ webUrl })` (kinds `post`, `machine`, `channel`, `today`, `calendar`; return `undefined` to keep the fallback). The fallback builds `${PUBLIC_ORIGIN}/app/<ws>/posts/:id`, `/machines/:id`, `/channels/:id`, `/app/<ws>` and `/app/<ws>/calendar?view=week&week=<monday>&event=publish:<post_id>` (§9.6). These routes must exist in `routes.tsx`.

## S10 (owner alerts)

7. **Alert stream teardown** (`modules/alerts/stream.ts`): with an authenticated stream open and cancelled by the client, a second request to the hub afterwards makes `app.close()` wait about 70 s (reproduced in a test: open stream → `body.cancel()` → another `fetch` to the stream → `app.close()`). Opening the stream last avoids it, so S4's test does that. Probably the server does not see the first socket close until a later write; worth a look before S8's E2E stack restarts hubs.
8. `registerAgentAlertStream` gets no `subscribe`: the `Store` interface has no `subscribe`, so the stream polls every second.

## S9 (Worker App) / S7 (agent-connect page)

9. **Re-connecting the same laptop** (§6.2 step 5) says the App revokes the old connection with `DELETE /agent-connections/:id`, but that route needs the owner's browser session and CSRF token, which the App does not have. Either the `/agent-connect` page (S7) revokes the previous connection of the same label/client before redirecting, or the lead adds a token-authenticated self-revoke for Agent connections to Appendix B. S4 did not add an endpoint outside Appendix B.

## S8 (E2E and real-model tests)

10. The S5 relay refuses media inside its own data directory, which is the directory of `--token-file`. Put the token file in a directory that does not contain the model's working directory (the first smoke run with `<tmp>/token` and `<tmp>/work/video.mp4` failed with `PATH_NOT_ALLOWED`).
11. `apps/server/src/integration/mcp-hub-tools.test.ts` is a working in-process reference: real app, Operation routes, `/mcp`, the S5 relay over in-memory stdio, an agent connection, and the §7.6 sequence.

## Lead (Appendix C, design text)

12. Codes S4 returns that Appendix C does not list: `TASK_NOT_FOUND` (404, `task_get`), `MACHINE_NOT_FOUND` (404, `publishing_pause` scope machine), `IDEMPOTENCY_MISMATCH` (422, a reused `request_id` with different arguments; existing code), `INVALID_STATE` (409, `channel_check` on a channel with no machine; existing code), `UNAVAILABLE` (503, an Operation not mounted). Warning codes in `posts[].warnings`: `caption_empty`, `caption_title_ignored`, `login_check_unavailable`, plus the precheck risk keys (`media_spec`, `machine_online`, `login_state`, …) and machine warnings (`sleep_enabled`, `no_auto_login`).
13.
