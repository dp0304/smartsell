## Confirmed as correct (no change)

- `blockUnsent`: never writes a Worker-route task; `approval_invalid` → `revokeForTarget(…, 'approval_invalidated')`; other reasons (`precheck_blocked`, 1-hour preflight) leave the job to go check + hold. Matches §4.4/§5.2.
- `hasExecutionRisk` unchanged: Worker task states `running`, `cancel_pending`, `outcome_unknown` are outside the refreezable set, so `checkEditable` returns `LEASE_HELD` exactly while the job may have an effect; every attempt end clears `active_attempt_id` in `syncTaskFromJob`, so missed/failed/mark-not-published posts become editable (tested).
- `submit()` bumps `snapshot_generation` when a task exists, which refreezes the task; `dispatchWorkerJob` is idempotent on (frozen hash, scheduled time), so a re-approval with the same content keeps the claimed job.
- `activatePause` / `releasePause` never revoke (§5.10 "暫停不撤回"); `ready()` on release calls `ensureTask`, which re-dispatches only when no live job exists (tested). Note: a pause cannot stop a job that already started (go is past); that is the design's rule, not a defect.
- `cancel()` retires the request before `requestCancellation`; the Worker-aware path throws `POST_LOCKED` / `POST_RESULT_UNKNOWN` and the transaction rolls back (tested in `dispatch.test.ts`).
- `approvalValid` channel_policy branch (direct + same `approval_generation`) is what go check 5 and the heartbeat `hold` use.
- `assessTarget` returns `route: 'worker'`; `ensureTask` writes `route = [{ executor: 'worker', device_id }]` and dispatches in the same transaction.
- `deviceOnline` reads `ctx.presence` (C14). S3 now injects it through `workspace-services.ts` (`presenceFor`), which also yields to a row that another code path stamped (worker-catalog claims, tests).

## Left as is, for the lead

- `channelDayUsage` (schedule precheck) counts `ready` targets; go check 7 counts running/published jobs of the local day. Different by design (§4.4 vs §5.4.4); S3 does not reuse `channelDayUsage` for go.
- `execution/ops.ts` human operations (`publishing_manual_complete`, retry, handover) do not know the Worker route. They are not on the phase 1 path (the hub uses `hub_posts_confirm_result`), but a person could still call them on a Worker task. Needs an owner decision (S3 owns only `execution/{service,worker}.ts`).
