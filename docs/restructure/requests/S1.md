# S1（中樞執行環境）對其他工作流的請求

S1 沒有修改下列檔案；以下是需要擁有者處理的變更，以及 S1 已提供的介面。

## 給 S5（媒體路徑）

1. **`apps/server/src/extensions/media-files.ts` `mediaStorageFromEnv()` 與 `apps/server/src/integration/media-host.ts` `createMediaHost()`：**依 §6.7 改成 `mediaStorageFromConfig(config)`，讀 `config.mediaDirectory`（S1 已提供，所有模式都等於 `MEDIA_DIRECTORY ?? join(dirname(statePath), 'media')`），並移除 `env.NODE_ENV === 'production'` 的直接讀取。
   - 理由：中樞模式下那一行讀 `NODE_ENV`，E2E 以 `NODE_ENV=test` 啟動時會走開發分支（`hub.test.ts` 的稽核清單已列出這一行）。
   - 過渡：`hub.ts` 目前會在 `start()` 之前設定 `process.env.MEDIA_DIRECTORY ??= config.mediaDirectory`，所以現在中樞的媒體已經落在 `<hubDir>/media`。改完後這個橋接可以留著，不影響。
2. 上傳大小上限請讀 `config.maxUploadBytes`（中樞 2 GiB、其他 512 MiB、上限 4 GiB）。
3. 上傳分段用 `PUT application/octet-stream`：根層守衛不檢查 PUT 的 Content-Type，已由 `hub.test.ts` 驗證（`/api/v1/agent/uploads/:id/parts/:n`）。若真的需要非 JSON 的 POST，用 `apps/server/src/app.ts` 匯出的 `RAW_BODY_ROUTE`（見 `docs/hub-setup.md` §9）。

## 給 S3（Worker job 引擎）

1. **Worker 安裝包的裝置簽章下載（§8.18、附錄 B.2）：**在掛裝置路由的地方（`integration/publish-device.ts` 或 `account/http.ts`，以 `publishing.mount(app, …)` 收到的根 app）呼叫：

   ```ts
   import { provideWorkerDownloadDeviceAuth } from '../worker-downloads.js';
   provideWorkerDownloadDeviceAuth(app, async (request, action) => {
     // action = 'worker_download.read:<platform>'；body 為空（rawBody = new Uint8Array()）
     // 以 x-smartsell-device/-timestamp/-nonce/-signature/-workspace 標頭，在短的唯讀交易內呼叫 authenticateDevice（含 NonceStore）
     // 失敗時丟出 Problem（401 等），成功時回傳任意值
   });
   ```

   尚未提供時，帶 `x-smartsell-device` 標頭的請求回 503 `DEVICE_AUTH_UNAVAILABLE`（不會假裝成功）。
2. **心跳 v2 的 `latest_worker`：**用 `workerReleases(config.workerDownloadDirectory)`（`apps/server/src/worker-downloads.ts`）取得各平台的 `{version, platform, file, sha256, bytes}`，`url` 用 `workerDownloadUrl(platform)`；比較版本可用 `compareWorkerVersions`。
3. **`GET /api/v1/device/driver-config` 與心跳的 `driver_config`：**檔案在 `config.driverConfigDirectory`（`<hubDir>/driver-config/selectors.json`），由 `pnpm hub:update` 放置；非中樞模式為 `undefined`，請回明確的錯誤而不是空設定。
4. **NonceStore：**以 `config.hub` 選擇記憶體實作（C8）。
5. 裝置的 `PUT /api/v1/device/evidence/:job_id`（octet-stream）不會被根層守衛擋下，已由 `hub.test.ts` 驗證。

## 給 S7（Web 與讀取模型）

1. `GET /api/v1/hub/info`（需登入，未登入 401）回傳 §2.7 的頂層欄位，同時在 `data` 底下鏡射同一個物件；`worker_downloads[]` 每項另外帶 `version`、`sha256`（可為 null）。第一次查詢時若 Tailscale 檢查尚未完成，會等最多 5 秒；`tailscale.serve_ok` 可能是 `null`（尚未檢查）。
2. 開發模式（`pnpm dev`）沒有這個路由（404），設定精靈請處理 404。
3. `GET /api/v1/worker-downloads` 的項目新增 `version`、`sha256`、`bytes`（原有的 `platform`、`filename`、`url` 不變）。
4. 中樞的 SPA 路徑只有 `/`、`/setup`、`/login`、`/worker-connect`、`/agent-connect`、`/app/*`、`/w/*`（附錄 B.4）。現有的 `/invite` 與 `/admin/*` 在中樞模式會回 JSON 404；若第 1 階段需要，請 lead 更新附錄 B.4，S1 再加入 `SPA_EXACT_PATHS`／`SPA_PREFIXES`（`apps/server/src/hub/web-static.ts`）。

## 給 S8（E2E 與真實模型測試）

1. 中樞子程序請設定 `SMARTSELL_TAILSCALE_CLI` 指向假的 CLI（或不存在的路徑），中樞每 10 分鐘的 `tailscale serve status` 才不會執行真的 tailscale。`hub.test.ts` 的完整啟動測試示範了假 CLI 的寫法。
2. 中樞模式拒絕這些開發開關：`SMARTSELL_WEBHOOK_LOOPBACK=1`、`SMARTSELL_AGENT_MODEL_LOOPBACK=1`、`SMARTSELL_LOCAL_SETUP=1`、`SMARTSELL_OPERATION_API=0`、`SMARTSELL_STORE≠local`。假 ntfy 伺服器若需要 loopback，請由 S10 的推播用自己的傳輸，不要依賴這些開關。
3. 根目錄已有 `test:e2e-phase1`（`node --import tsx --test tests/e2e-phase1/*.test.ts`）與 `real-model-check`（`node --import tsx scripts/real-model-check.mjs`）。
4. `hub.ts` 在 `NODE_ENV=test` 時保留 `test`；`config.testTiming` 讀 `SMARTSELL_TEST_OFFLINE_STALENESS_SEC`、`SMARTSELL_TEST_READBACK_SCHEDULE_SEC`（逗號分隔）、`SMARTSELL_TEST_UNREPORTED_GRACE_SEC`、`SMARTSELL_TEST_PREPARE_LEAD_SEC`。

## 給 S9（Worker App 殼與安裝包）

1. 根目錄 `worker:release` 為 `node --import tsx scripts/worker-release.mjs`。`pnpm hub:init` 會呼叫 `pnpm worker:release --out <hubDir>/worker-downloads`。
2. `latest-<platform>.json` 必須是 `{version, platform, file, sha256, bytes, built_at}`：`version` 為 `major.minor.patch[-pre]`，`file` 為同一資料夾內的檔名（`.zip`、`.dmg` 或 `.exe`，不含路徑），`sha256` 為 64 位小寫十六進位，`bytes` 等於檔案大小。不符合時中樞不提供該平台的下載，`hub:doctor` 會報錯。
