# S7 (Web pages and read models): requests to other workstreams

S7 owns `apps/web/**`, `apps/server/src/modules/workspace/views/**`, `apps/server/src/modules/workspace/overview.ts` and (E15)
`apps/server/src/modules/posting/{views.ts,posts.ts}`. Everything below is a change in a file S7 does not own, or a contract other
streams code against. Closure of the items addressed to S7: `closure-S7.md`.

## What S7 provides

- **C7 builders** (`apps/server/src/modules/workspace/views/index.ts` re-exports them): `buildOverview(ctx)`, `buildToday(ctx, tz?)`,
  `machineSummaries(ctx, {includeOffline?})`, `machineDetail(ctx, id)`, `machineWarnings(ctx, device, 'zh'|'en')`, `channelSummaries(ctx, filter)`,
  `channelDetail(ctx, id)`, `postSummary(ctx, targetId)`, `postDetail(ctx, targetId)`, `listPosts(ctx, query)`, `jobDetail(ctx, jobId)`.
- **Operations** (module `workspace`, READ): `views_overview`, `views_today`, `views_machines_list`, `views_machine_get`, `views_channels_list`,
  `views_channel_get`, `views_posts_list`, `views_post_get`, `views_job_get`, `views_media_recent` (paths of §9.7). Unknown query parameters
  answer 422 `INVALID_ARGUMENTS` with the issue path.
- **Links** (§9.6): `webUrl(ctx, kind, id?)` in `views/links.ts`, kinds `post`, `machine`, `channel`, `today`, `calendar` (with a post id it opens that
  post's week and drawer), `notifications` (S10's push settings page, `/settings/notifications`), `alerts` (the list behind the bell,
  `/notifications`), `channels`, `machines`, `setup`. `machines.test.ts` checks that every kind maps to a route defined in `routes.tsx`.
- **`installWebLinks({ publicOrigin })`** (`views/install.ts`): sets the origin for `webUrl` and registers it with S4 (`configurePosting({ publicOrigin, webUrl })`)
  and S10 (`configureAlerts({ webUrl, machineWarnings })`).
- **Web routes** under `/app/:ws`: index → Today, `overview` (old overview), `machines`, `machines/:id`, `channels`, `channels/:id`, `posts/:id`,
  `notifications`, `settings/notifications`; `settings/worker-accounts` redirects to `channels`. Top level: `/agent-connect` (S9's App).

## L-server (server bootstrap)

1. **Call `installWebLinks` once at startup**, before the background drains run — `apps/server/src/bootstrap.ts` (S1/S3/L-server):

   ```ts
   import { installWebLinks } from './modules/workspace/views/install.js';
   installWebLinks({ publicOrigin: config.origin });
   ```

   Without it every `web_url` (MCP results, owner alerts, push messages) uses the fallback origin `process.env.PUBLIC_ORIGIN ?? http://127.0.0.1:<PORT>`,
   which is wrong behind `tailscale serve`, and S10's `machine_setup` alerts use S10's reduced warning set instead of the §3.2 one.
   **Status:** observed wired in `apps/server/src/bootstrap.ts` (dynamic import after `discoverOperations()`, then `installWebLinks({ publicOrigin: config.origin })`).
   Note for S10: `machineWarnings` includes `sync_behind` only after a change has been missed for 60 s, so a settings save does not raise a
   `machine_setup` alert for a machine that simply has not sent its next heartbeat yet.

## Lead / S0 (`apps/server/src/operations.ts`)

2. **`limit` never reaches `views_posts_list`.** `runScopedOperation` strips `cursor` and `limit` from every GET query before `run()` (they drive array
   pagination), so §9.7's `views_posts_list?limit=` cannot be honoured: the result is an object `{posts, total, truncated}`, not an array. S7 reads up to
   200 posts per request and reports `truncated`; the Agent tool `posts_list` passes its own `limit` and is not affected. Suggest passing `limit` through
   when the operation's result is not an array (or renaming the view parameter in §9.7).
3. **Appendix A `derivePostStatus` and a force-released unreported job** (S3 ledger 8): the job is `cancelled`, the task `blocked`, the post still
   `ready`, so the frozen function says `scheduled` although nothing will run. S7's `postStatus` (views/hub-model.ts) feeds it `job_status: 'missed'` in
   exactly that case, so every page and the Agent show 「沒有發出」 with 「改到…」. Please amend Appendix A so the rule lives in the contract.
4. **`PostGroup` additive fields**: `views_today.upcoming[]` carries `title` (content title, else the media file name) and `media_filename`, so Today can say
   「video.mp4 → X + TikTok」. Please add them to Appendix A or tell S7 to drop them.

## S4 (`modules/posting/check.ts`, `schemas.ts`)

5. **「重新登入」 has no endpoint.** §8.16 step 7 says the channel page's 「重新登入」 creates `check_login{open_login_window:true}` on that machine. The only
   web-callable path, `hub_channels_check`, takes `{}` strictly and always creates `openLoginWindow: false` (only `hub_channels_bind_machine` opens the
   window). Please accept `open_login_window?: boolean` on `hub_channels_check` for a person (reject it for an Agent credential), or add a human-only
   `hub_channels_relogin`. Until then the web offers 「檢查登入」 and tells the owner to press 「重新登入」 in that machine's SmartSell Worker (the Worker App has
   the button, §8.17); it does not pretend to open a window.

## S3 (`modules/worker/*`)

6. **After a direct → needs_approval change, a claimed job stays live.** In the view fixture (`hub_channels_update_settings {approval_mode:'needs_approval'}`
   on a direct channel whose post's job is `claimed`), the target goes to `awaiting_approval` but the job stays `claimed` with no `revoke`, so
   `derivePostStatus` (live job first) shows `scheduled` while the post waits for approval. Please confirm that `go` denies it (`approval_invalid`) and,
   per §4.1/§5.10, revoke the job (`approval_invalidated`) so the views show 「待你核准」.
