# S10 (owner alerts): requests to other workstreams

S10 owns `apps/server/src/modules/alerts/**` and `apps/server/src/modules/workspace/notifications.ts`. Everything below is a change in a file S10 does not own. Each item names the file, the function, the exact change and why. The alerts module already works without these (schedules and subscribers are picked up by `discoverOperations`); they wire the parts that need host access.

## S1 (hub runtime): `apps/server/src/bootstrap.ts`, `optionalOperationApi()`

1. **Run the alerts drain** so phone push is sent outside every transaction (§11.2 C13: "推播在交易外送出（先寫 owner_alert，再由 S10 的背景工作發送）", §0 principle 8). Without this, alerts reach the bell and the alert stream but no phone push is sent.

   ```ts
   import { configureAlerts, createAlertsDrain } from './modules/alerts/index.js';
   // in optionalOperationApi(), next to the other drains:
   const alertsDrain = createAlertsDrain();
   const drain: BackgroundDrain = async transact => {
     await drainCommerce(transact);
     await signedWebhook.drain(transact);
     await publishing.drain(transact);
     await alertsDrain(transact);
   };
   ```

   The drain also scans the time-based reminders every 15 s (approval T−60/T−10, click-post at not_before − prepare_lead_min and not_before, machine offline, machine setup, 21:00 summary). The 60 s `alerts.reminders` schedule stays as a fallback; both are idempotent.

2. **Give the alerts module the hub key and origin** (push tokens are sealed at rest, §3.1 `alert_channel`; links use `PUBLIC_ORIGIN`). Call once before the background starts:

   ```ts
   configureAlerts({
     secretKey: createHash('sha256').update(`smartsell:alert-channel:v1:${config.secret}`).digest(),
     publicOrigin: config.origin,
   });
   ```

   Without it the module falls back to `process.env.APP_SECRET` and `process.env.PUBLIC_ORIGIN`; when neither key source exists, saving a token returns 503 `ALERT_SECRET_UNAVAILABLE` (explicit, never a plaintext write).

## S4 (MCP and agent credentials): `apps/server/src/integration/command-mcp.ts`

3. **Mount the alert stream** after `/mcp`, as C4 specifies:

   ```ts
   import { registerAgentAlertStream } from '../modules/alerts/index.js';
   registerAgentAlertStream(app, { credentials, subscribe: store.subscribe?.bind(store) });
   ```

   `credentials` is the C4 `AgentCredentialService`. S10 codes against a structural copy (`AlertStreamCredentials` in `modules/alerts/stream.ts`): `authenticate(req)` returns a principal whose `run(false, fn)` opens a read-only workspace transaction. `subscribe` is optional (immediate wake-up instead of the 1 s poll). The route is `GET /api/v1/agent/alerts/stream`, read-only, `Last-Event-ID` (or `?last_event_id=`) resume, optional `?machine_id=`.

## S3 (Worker job engine): `apps/server/src/modules/worker/*`

4. **Emit `worker.job.status_changed`** exactly as C3: `{ job_id, from, to, publish_target_id, social_account_id, device_id, blocker_code }`, for every status change, after the `worker_job` row is updated in the same transaction (the subscriber reads the row for `kind`, `dry_run`, `not_before`/`not_after`, `blocker`, `resume_token`, `result`, `waits_for_job_id`). Alerts produced: needs_owner → `worker_blocker` (or `click_post_soon` for `owner_click_required`); failed → `worker_blocker`; missed → `missed`; outcome_unknown/unreported → `unknown`; succeeded → `published`; check_login needs_owner/failed → `login_check_failed`.
5. **Missed reason:** write the reason into the `worker_job_event` S3 already records: device `missed` with `detail.reason`, or the hub events `missed_unclaimed` / `missed_machine_off`; for go denials that end in missed (`daily_cap_reached`, `outside_window`) write an event `missed` with `detail.reason` set to that code. The alert text names the reason from there.
6. **Successor auto-cancel (§5.2):** write the `successor_cancelled_predecessor_posted` event on the successor job before (or in the same transaction as) its status change to `cancelled`; or emit `worker.job.late_fact { job_id: <predecessor>, publish_target_id, successor_cancelled: true }`. Either path yields one urgent `late_fact_after_release` alert (deduped by the predecessor job id).
7. **`offline_run_used_stale_settings` (§5.4.3 "通知主人")** has no `OwnerAlertKind` in Appendix A. Until the lead decides, call `raiseAlert(ctx, { kind: 'unknown', severity: 'normal', dedupe_key: `${job.id}:stale_settings`, … })` or ask the lead to add a kind.
8. Alternatively S3 may call the helpers directly (`alertJobStatus`, `alertLateFact` from `modules/alerts/index.ts`); they are idempotent with the subscriber.

## S5 (media path): `apps/server/src/integration/agent-uploads.ts`

9. **`upload_failed`:** in the short transaction that marks the upload's asset `failed` (abort, `UPLOAD_HASH_MISMATCH`, hourly expiry cleanup), call
   `alertUploadFailed(ctx, { media_id: asset.id, filename, reason })` with `reason` one of `file_changed | cancelled | error | expired | UPLOAD_HASH_MISMATCH | UPLOAD_EXPIRED`.
10. **`upload_done`:** set `asset.origin = 'agent_upload'` and `asset.status = 'ready'` before emitting `asset.version.created` (§6.4 step 3.4). The alerts subscriber turns that into `upload_done`; calling `alertUploadDone(ctx, { media_id, filename })` directly is also fine.

## S2 (channels and approvals): `apps/server/src/modules/account/channel-settings.ts`

## S7 (web and read models)

13. `apps/server/src/modules/workspace/views/*`: when `webUrl(ctx, kind, id)` exists, register it with `configureAlerts({ webUrl, machineWarnings })` (kinds S10 uses: `post`, `machine`, `channel`, `today`, `notifications`). The fallback builds `/app/<ws>/posts/:id`, `/machines/:id`, `/channels/:id`, `/app/<ws>`, `/app/<ws>/settings/notifications` and derives only `sleep_enabled`, `no_auto_login`, `clock_skew`, `driver_outdated`.
14. Bell: `views_alerts` (`GET /views/alerts?unread=true|false`, `OwnerAlert[]` newest first) and `hub_alerts_read` (`POST /hub/alerts/read {ids:[…]} | {all:true}` → `{updated, unread}`). Every new alert emits `alerts.owner_alert.created`, which bumps the workspace stream revision, so `useViewStream` refetches. `OverviewView.alerts.unread` = unread count of `owner_alert` rows.
15. Settings → 通知: `hub_alerts_get_channels` returns `{channels: (AlertChannelConfig & {id, enabled, last_test, last_delivery})[], preferences: {published, daily_summary}, settings_url}`; `hub_alerts_update_channels` (PUT) takes `{channels?: [{kind:'ntfy', url, token?: string|null} | {kind:'bark', url} | {kind:'telegram', chat_id, bot_token?: string|null}], preferences?: {published?, daily_summary?}}` (omitted token keeps the stored one, `null` clears it); `hub_alerts_test` (POST, 202) returns `{test_id, status:'queued', channels}` and the result shows up in `last_test` within one drain cycle. ## S9 (Worker App): laptop Agent mode

16. Subscribe to `GET /api/v1/agent/alerts/stream` with the agent connection token; store the last `id:` and send it back as `Last-Event-ID` on reconnect (the server sends `retry: 2000`). A fresh subscription starts at the newest alert (no history replay). Events are `event: owner_alert`, `data: OwnerAlert`; open `web_url` on click. The Worker App's own notifications can pass `?machine_id=<own device id>`.
