# SmartSell 逐項審核與重新編排計畫

日期：2026-11-24　範圍：Gitee `master@0d9d836`、GitHub 社群版 `main@163a9d0`
方法：10 位審核員分區實測（讀程式碼並實際跑流程，含真實 Claude Code 用戶端），1 位整合、1 位挑錯；平台規則以官方文件查證。

## 0. 結論

**現在能用的：** 註冊、機器配對的簽章協定、把帳號或商店綁到機器、讀取類查詢、核准卡、計劃詳情頁、緊急暫停。

**不能用的正好是核心：**
- Worker 不會發布、不會採集數據、不會讀留言。
- 別台機器連不進來（只聽本機），也沒有安裝包可以下載。
- Codex 傳不了真實大小的影片（上限 512 KB）；「明天 9 點發 TikTok」實測要 42 次工具呼叫、14 次錯誤，結果只是草稿。
- 每一步都要人做，做完還是落到「人工發布」。
- 好幾個操作回「成功」卻沒做事（改時區、改價、送出回覆）。

**根本原因：** 系統做成了 19 個模組、約 990 個操作的企業套件，有兩套資料模型、四五個網頁入口；願景真正要的「Codex → 機器 → 平台 → 結果回來」反而最薄。

**做法：** 先做出一條真正能用的閉環，再大幅收斂。下面第 2 節是重新編排後的計畫；第 3–5 節是逐項審核的完整紀錄。

## 1. 主人已做的決定

| 問題 | 決定 |
|---|---|
| Codex 說要發，要不要在網頁按核准 | 每個帳號自己設定：「直接發」或「要我按核准」 |
| 範圍 | 只做核心；其他模組在網頁與 Codex 中隱藏，程式碼保留 |
| 先支援的發布平台 | TikTok、YouTube Shorts、Instagram／Facebook、X |
| 兩個倉庫 | 保持同步（每次公開推送 GitHub 前再確認一次） |
| 中樞放哪裡 | 一台常開的家用機器＋Tailscale |
| TikTok、X 怎麼發 | Worker 在該帳號的 Chrome 全程代操作，包含按「發布」 |
| Codex 何時做事 | 只在主人打開 Codex 時；網頁顯示「Codex 有 N 件待辦」 |

**關於 TikTok、X 的瀏覽器代操作（已查證，請知悉）：** X 的自動化規則明文寫著「以非 API 方式自動化，例如以腳本操作 X 網站，可能導致帳號被永久停權」；TikTok 條款也禁止以自動化方式操作。因此：
- 每個帳號要單獨勾選「我了解平台條款風險，允許 Worker 代按發布」，勾選會記錄在活動紀錄；沒勾選的帳號，Worker 準備好後停在發布按鈕前，通知主人按。
- 只用該帳號那台機器上的原版 Chrome；不偽造指紋、不改裝置識別碼、不用模擬器、不規避偵測、不解驗證碼、不做帳號農場。遇到驗證碼、二次驗證、風控提示一律停下並通知主人。
- 每個帳號有每日上限與時段限制。

YouTube、Instagram、Facebook 的官方 API 對自己的帳號可以免費、合規地自動發布（查證見附錄 A）。預設同樣由 Worker 在瀏覽器代操作；帳號頁可以改用官方 API。

**我先採用的預設（之後可改）：**
- 資料：重新開始，舊資料提供匯出，不做自動搬移。
- Worker 安裝包：先出未簽章版本並附安裝說明；Apple Developer ID 與 Windows 簽章憑證需要主人申請，到時再接上。
- 商店：先做「只讀」（拉商品、價格、庫存）；改價、改庫存、上下架放到後面，每次都要核准。

## 2. 重新編排後的系統

### 2.1 一句話
SmartSell 是主人的 Codex 與各台機器之間的**調度中心**：Codex 交代事情，中樞決定由哪台機器做，機器在該帳號的 Chrome 裡做，結果回到中樞，網頁把「機器 → 帳號 → 貼文 → 結果 → 留言」和「商品 → 內容 → 貼文」串起來給人看。

### 2.2 核心物件
| 物件 | 是什麼 |
|---|---|
| 機器 Machine | 一台配對好的 Worker：名稱（主機名）、在線狀態、版本、佇列 |
| 帳號 Channel | 一個社媒帳號或一家商店；綁在一台機器上（或改用官方 API）；有登入狀態、執行方式、核准設定、每日上限 |
| 商品 Product／上架 Listing | 主商品＋它在各家店的樣子（價格、庫存、網址） |
| 媒體 Media | 影片或圖片；自己上傳的預設為自有 |
| 貼文 Post | 一段內容發到一個帳號的一次排程：時間、時區、狀態、由誰執行 |
| 任務 Task | 機器要做的一件事：發布、檢查登入、讀數據、讀留言、送回覆、拉商品 |
| 平台貼文 PlatformPost | 平台上真的存在的貼文：網址、外部 ID；連回貼文 |
| 數據 Metric | 帳號或貼文某一天的數字（未採集就是未採集，不當 0） |
| 留言 Thread／Reply | 留言與私訊，掛在平台貼文下；回覆由任務送出 |

路由只有一條規則：**任務由帳號決定在哪裡做。** 帳號綁哪台機器就派給哪台；綁官方 API 就走 API；機器離線就等待，並在「今日」頁顯示「Mac-B 離線，3 個任務等待中」，絕不派給別台。

### 2.3 給 Codex 的工具（約 20 個，完整型別、不認得的欄位一律回錯）
`smartsell_overview`、`machines_list`、`channels_list`、`channel_check`、`media_upload`、`post_schedule`、`post_update`、`posts_list`、`post_get`、`task_get`、`publishing_pause`、`stats_collect`、`stats_get`、`comments_list`、`reply_draft`、`reply_send`、`products_search`、`product_get`、`products_import`、`agent_jobs`。
舊的 100 個具名工具與 700 多個通用操作預設不給 Codex；替代工具通過同一個真實模型測試後，舊工具才移除。

### 2.4 Worker 怎麼做事
1. 常駐、開機自啟、自動連線，斷線自己重連。
2. 每個帳號一個獨立的 Chrome profile（原版 Chrome）。
3. 單一任務佇列；任務在排程前就派到機器上，Worker 提前下載並校驗媒體、確認登入；到點準時執行，中樞短暫停機也照做，事後回報。
4. 遲到上限（預設 30 分鐘）：機器離線過久，過了上限就不補發，改請主人決定。
5. 發完讀回貼文網址當結果；暫時讀不到就繼續對帳，不會自動重發。
6. 遇到驗證碼、二次驗證、登入過期、風控：停下，通知主人（指名哪台機器、哪個帳號）。

### 2.5 網頁
今日（要你處理的事、今天的排程、離線機器）｜機器｜帳號與商店｜日曆與貼文｜商品｜留言｜數據｜Agent｜設定。每一筆都連到上下游；所有「請你的 Agent…複製」改成「交給 Agent」按鈕（放進 Codex 待辦）。舊工作台 /w 在功能搬完後隱藏，/compat 移除。

### 2.6 分階段
| 階段 | 內容 | 完成標準 |
|---|---|---|
| 1 最小閉環 | 中樞服務＋Tailscale 連線；Worker 常駐；帳號 X／TikTok 的瀏覽器發布驅動；大檔上傳；`post_schedule` 一次排好；結果回流；今日、機器、帳號、貼文頁 | 在筆電的 Codex 說「把 video.mp4 明天 9:00 發到 Mac-B 的 X 和 Win-C 的 TikTok」，6 次以內的工具呼叫；到點兩台機器各自發出，5 分鐘內網址回到 SmartSell，各頁一致且互連；中樞 8:55–9:10 停機照樣發；機器離線超過遲到上限不補發 |
| 2 收斂與誠實 | 刪除 Commands 模型、/compat、kernel 入口與膠水程式；資料改成逐筆存（不再整包重寫）；隱藏非核心模組；「不准假成功」清單全部修好並有測試；註冊時問名稱、時區、幣別；併入社群版的簡體中文 | 只剩一個資料模型；清單逐項測試通過；新工作區日曆用本地時間 |
| 3 更多平台 | YouTube Shorts、Instagram、Facebook 的瀏覽器驅動；可選的官方 API 路徑 | 五個平台各有一次真實帳號發布紀錄（由主人在自己的機器驗收） |
| 4 數據回流 | Worker 讀自己帳號後台的數據頁；每天自動採集；帳號頁、貼文頁的趨勢 | 3 個帳號連續 7 天自動有粉絲數與播放數；各頁數字一致 |
| 5 留言與回覆 | Worker 讀自己貼文的留言與私訊；打開 Codex 時起草回覆；依帳號設定核准；Worker 送出並讀回確認 | 新留言 30 分鐘內出現並連到貼文與商品；回覆送出後讀回確認 |
| 6 商品與商店 | 主商品＋各店上架；Worker 在已登入的商店後台拉商品；之後再做改價、改庫存（每次核准） | 同一 SKU 在兩家店只顯示一個商品；拉取不需要有人在遠端機器操作 |
| 7 安裝包與兩倉同步 | Mac（arm64／x64）、Windows 安裝包與自動更新；CI；同步 GitHub 社群版（推送前確認） | 新機器下載安裝後 15 分鐘內配對完成；兩倉內容一致 |

**我能驗證與不能驗證的：** 我會用本機的模擬平台頁面與模擬 Worker 跑完整閉環測試，並用真實的 Claude Code 測工具好不好用；但我不會登入主人的真實社媒帳號，所以每個平台驅動的「真實發布」需要主人在自己的機器上按一次驗收（驅動附「試跑」模式：走到發布前一步就停）。

## 4. 為什麼現在不能用

以下依影響大小排序。每一條都附報告中的實測證據。

### 4.1 Worker 只會陪人做，自己不執行
願景中負責動手的是 Worker，但現在沒有任何一條路能讓 Worker 把貼文發出去。
- 抖音、小紅書必填 visibility 選項；只要選項不是空的，publish-connector.ts:26 就不編碼。結果每一則都落到 manual_fallback（B-EX1 到 0d9d836 仍未修）。
- 另外還要手寫 SMARTSELL_CONNECTOR_APPROVALS 環境變數 JSON，而且綁定 client_version，Worker 一更新就失效。
- 就算任務真的派到了，Worker 也會卡住：
  - 自動送出直接拋錯（controller.ts:975）。
  - 媒體不會送到那台機器。
  - 回報證據在正式環境一律回 422。
- 平台只支援抖音和小紅書，沒有 X、TikTok、YouTube、IG。
- 實測：排在 75 秒後的 IG 貼文，到點 15 秒後變成 `manual / awaiting_assignee`，沒有派給任何 Worker。

### 4.2 別台機器連不進來
- 本機模式只綁 127.0.0.1，桌面端只接受 https 或 localhost。
- 正式模式要 PostgreSQL 17、三個角色、RLS、TLS 反向代理。
- 沒有安裝包可以下載。只有 Apple 晶片的 Mac 能自建，Windows 從未建置過。
- Worker 開機後不會自動連線，心跳斷一次就停住，等人按連線。
- 發布租約要求排程後 30 分鐘內有人在機器前。
- 跨兩台實體機器、Windows 安裝，lab 的 README 自己寫著「仍待實機驗證」。

### 4.3 Codex 寫不進核心流程
- 100 個工具中有 90 個不列欄位，另外還有 703 個通用操作。實測時模型要猜這些欄位：
  - template_key、csv_text、base64、file_object_id；
  - 時間不能帶秒，而這點沒有記載。
- 影片上傳上限是 512KB。30MB 的影片會讓 MCP 連線斷掉；用 Agent 權杖 PUT 回 401。
- 實測成本：
  - 「明天 9 點發 TikTok」：42 次呼叫、14 次錯誤、$2.37，最後只是草稿。
  - 匯入 3 個商品：33 次呼叫、$1.10。
- 沒有任何工具能指定機器，也看不到有哪些機器（`account_list_devices` 回 TOOL_UNAVAILABLE）。

### 4.4 每一步都要人，不能委派，而且介面和 Agent 互相推給對方
- 自己拍的影片也要人逐一啟用使用權。TikTok 和小紅書的選項只能人選。人一改就產生新版本，target 要重新指向、重新送審、重新核准。
- 核准只能由人做。optional 政策對 Agent 無效，常設授權只有測試能建立。
- 核准之後還是落到人工發布。結果主人做的事比不用 SmartSell 還多。
- 日曆抽屜叫主人「請你的 Agent」，但 Agent 去讀 manual bundle、去登記貼文都回 HUMAN_REQUIRED。這時「待你決定」頁卻顯示沒有東西。

### 4.5 資料不會自己進來
- **社媒數據：** Worker 只回報登入狀態；官方同步回 SOURCE_UNAVAILABLE；Agent 被禁止自己去抓。最後只剩手工 CSV。
- **留言：** 沒有同步，沒有 webhook，Worker 也不讀。唯一的入口是手動呼叫 inbox_ingest_batch。
- **商品：** Worker 匯入要有人在遠端機器手動匯出、上傳。Worker 商店的 sync 回 STORE_NOT_CONNECTED。
- **X：** 主人的主要渠道，但無法登記成帳號（422），所以 X 的資料都進不了任何頁面。

### 4.6 兩套資料模型、兩個伺服器、三個網頁
- Commands（577 個指令）與 Operations（990 個操作）的資料不同步：
  - 實測兩邊建的品牌互相看不到。
  - Commands 的緊急暫停，Operations 看不到。
- 伺服器各缺一半：
  - kernel 有 OAuth，卻沒有 Agent 接入。
  - command-main 有接入，卻沒有 OAuth。
  - 兩者用不同的資料檔。
- 網頁有三個：/app、/w（19 個模組）、/compat（顯示 0 筆），還有三份上手清單。/app 仍要連到 /w 才能做平台授權、成員管理和檔案匯入。
- 約 6,600 行膠水程式和雙份測試，只是為了讓這兩套模型能互通。

### 4.7 頁面沒把東西串起來
- **機器：** 沒有機器頁，也沒有帳號頁。總覽、日曆、社媒、計劃、待你決定，都不提機器。
- **商品：** 商品和貼文只透過 content_reference 關聯，而 Agent 路徑從不建立這個關聯，所以 6 個商品全部顯示「沒有發布」。
- **帳號：** Worker 登記的帳號被丟進自動建立的「Worker channels」品牌，用真品牌篩選反而看不到。
- **日曆與留言：** 日曆抽屜沒有帳號、機器、媒體。留言的 platform_post_id 是自由文字，沒有程式去讀。
- **Worker 結果：** 只出現在開發者用的 MCP 審計裡，顯示的是 UUID。

### 4.8 回報成功，但沒有做事
這是信任問題。主人無法從回應判斷事情到底有沒有做。
- workspace_update 帶 timezone，回成功但沒改。
- commerce_record_listing 要改成 3500，回成功但存成 3900。
- query.platform 被默默忽略，回傳了其他平台的資料。
- 回覆留言：
  - inbox_send_reply 回成功，其實只是記下「需要有人去發」。
  - Agent 用假網址就能把回覆標成已送達。
- 庫存規則、desktop_request_capability、自動回覆規則，都只存一筆紀錄。
- 活動動態把被擋下的送審寫成「送審了」。YouTube 的 insights_read 標成 implemented，實際上沒有執行器。

### 4.9 範圍做成了企業套件，核心反而最薄
- 990 個操作中，約 45%（443 個）不在願景內。例如：
  - 達人 CRM、Email 行銷；
  - 落地頁、短網址、代理商入口；
  - 租戶管理、廣告治理、歸因、實驗；
  - 平台內的模型閘道。
- 收件匣照客服中心設計（SLA、案件、租約、fencing），卻沒有任何資料會進來。
- plan.md 有 1.1MB、規劃 147 項功能，讓範圍一直縮不下來。

### 4.10 上手流程又長又脆
- 約 17 步：23–27KB 的 Python 腳本、10 分鐘有效的一次性碼、完整重開用戶端、再貼核對句。途中出現約 35 個術語。
- Codex 路徑沒裝 CLI 就失敗，頁面上沒有說。
- 工作區預設為 SmartSell、UTC、USD，所以日曆差 8 小時、粉絲數晚一天。
- 每 90 天要重做一次。多台機器的連線名稱都一樣，分不出來。

### 4.11 驗收量錯了東西
- 「140 個原生 Claude Code 回執」用的是 loopback 腳本 fixture，背後沒有模型。
- 701 個閘道操作中只有 154 個通過業務斷言，357 個從未執行。
- 影片場景是用 SDK 上傳的，不是 Agent。Worker 發布的驗收寫著「本輪止於預檢」。
- 784 個測試幾乎都在證明單一功能可行，沒有一個測「Codex → Worker → 平台 → 結果」。

### 4.12 兩個倉庫已經分岔
- 歷史沒有共同祖先。Gitee 多 302 個檔案；GitHub 多 6 個提交（簡中、三語文件、Compose 修正）。
- 主人用的主線沒有簡中介面。公開版缺整個 Worker 層，也沒有 LICENSE。
- 下次合併會把已經清掉的示範帳號、+886 電話、內部雜湊帶回公開倉庫。

## 5. 對照願景的缺口

### 5.1 連接 Agent（Codex／Claude）
- **現有：**
  - MCP 端點可用，Claude Code 的引導接入能跑通。
  - 讀取類工具答得對；人工專屬邊界有效；有呼叫審計。
- **壞的或缺的：**
  - 接入要約 17 步，Codex 路徑失敗；「已驗證」狀態不準；不能續期；多台機器的連線分不出來。
  - 有三份工具目錄（100、103、42 個工具），工具沒有 schema，不認得的欄位和篩選被默默忽略。
  - 網頁交辦的任務不會送到 Codex。
- **需要：**
  - 一行指令接入，或由桌面 App 代辦；名稱固定為 smartsell。
  - 第一次成功呼叫就算已連線；自動續期。
  - 約 20 個完整型別的工具；嚴格驗證；每個結果都帶網頁連結；Skills 隨安裝包發布。

### 5.2 配對機器
- **現有：** 簽章配對、心跳、帳號與商店綁到機器、緊急停止。
- **壞的或缺的：**
  - 沒有安裝包；只能 loopback；沒有支援的多機拓樸；不會自動連線。
  - 網頁沒有機器頁，Agent 也看不到機器。
  - Windows 未驗證；每台只有一個 Chrome profile。
  - 登記的帳號掉進「Worker channels」；X 不能登記。
- **需要：**
  - 一種官方支援的中樞拓樸；簽章安裝包；Worker 做成背景服務。
  - 機器頁和 machines_list。
  - 每個帳號一個 Chrome profile；配對時選品牌；新增 X provider。

### 5.3 商店與商品
- **現有：**
  - 能建店、綁機器，匯入任務會派到正確的機器。
  - 檔案匯入可用；商品詳情與市場快照可用；商品頁連得到計劃。
- **壞的或缺的：**
  - Worker 匯入要有人在遠端手動匯出；中文表頭被拒；價格被刪。
  - 改價是假成功；不能寫入商店。
  - 沒有主商品，同一個 SKU 變成兩個商品；沒有圖片；商品和貼文的關聯是空的。
  - API 連接要改環境變數；Commands 裡還有第二份目錄。
- **需要：**
  - 主商品加各店 listing；只留一個匯入對應器；Worker 自己拉取商品。
  - 在網頁內連接商店 API。
  - （主人決定後）寫入任務，並回傳回執。
  - 商品頁串到貼文和成效。

### 5.4 製作影片並經 Worker 發布
- **現有：**
  - content_create_draft 一次建立草稿；時區轉換正確。
  - 預檢、核准綁版本、fencing、outcome_unknown 的設計是對的。
  - 到期排程器準時；YouTube 可以上傳私人影片。
- **壞的或缺的：**
  - Agent 傳不了大影片；X 不能當發布目標。
  - 人工關卡層層疊加：選項、使用權、逐則核准、重新指向。
  - Worker 端有 encode 閘和環境變數核准閘，只能協助人，媒體不會送到，證據回報 422。
  - IG／FB／TikTok 的 adapter 沒接上，所有貼文都落到人工；/app 沒有人工發布卡；結果無法回報。
- **需要：**
  - 一次性上傳網址；post_schedule 一次完成；帳號層級的預設選項；自治政策。
  - 修好 encode，刪掉環境變數閘；用簽章網址下載媒體。
  - X 與 TikTok 的瀏覽器驅動；接上官方 adapter；自動回執。
  - 貼文頁。

### 5.5 社媒數據
- **現有：** 社媒頁正確處理未知值與覆蓋率；CSV 和 JSON 寫入可用；廣告數據匯入後看得到。
- **壞的或缺的：**
  - 沒有收集器；X 不能登記；粉絲數晚一天。
  - 四個讀取 API 結果不一致；舊貼文的本週數據拿不到。
  - 匯入慢，還要用內部 UUID 格式；Worker 的結果停在任務列。
- **需要：**
  - stats_collect（Worker 或 API）；只留一條讀取路徑、一套指標鍵；以 report_day 記錄。
  - 帳號頁顯示所在機器；支援平台原生匯出檔。

### 5.6 留言與自動回覆
- **現有：** 對話串接與去重；Codex 起草回覆；人核准（Agent 被擋）。
- **壞的或缺的：**
  - 沒有任何收集；「送出」其實沒送；API 派送是死碼。
  - Agent 能把沒送出的回覆標成已送達；自動規則不會觸發。
  - 對話串不連到貼文或商品；/app 沒有留言頁；沒有具名的收件匣工具。
- **需要：**
  - 用 API 加 Worker 收集留言，並連到貼文與商品。
  - 派送器走 API 或持有帳號的機器；只有回讀能確認送達。
  - 回覆政策；留言頁；約 4 個工具。

### 5.7 串連的儀表板與日曆
- **現有：**
  - /app 頁面整潔，手機和英文模式都可用。
  - 計劃詳情串得最好；日曆有月、週、列表檢視。
  - 核准卡、緊急暫停可用。
- **壞的或缺的：**
  - 沒有機器、帳號、留言、內容頁；日曆抽屜沒有帳號、機器、媒體；商品頁沒有貼文。
  - 時間是 UTC；數字跨頁不一致。
  - 20 個「複製提示」框；三個介面；英文與原始字串外漏；審計只顯示 UUID。
- **需要：**
  - 以貼文為主軸，各頁用同一張貼文卡。
  - 機器頁、帳號頁、留言頁。
  - 「交給 Agent」按鈕；技術資訊收進開發者模式；只留一個介面。

## 附錄 B　挑錯者的主要修正（已併入第 2 節）

1. 平台條款：TikTok、X 的瀏覽器自動發布違反平台條款，改為每帳號勾選並記錄（主人已決定採用）。
2. 協助模式不能要求人在遠端機器前：改成任務提前派送與準備，自動模式由帳號設定決定。
3. 大檔上傳不能依賴 Codex 沙箱內的 `curl`：由桌面 App 在本機提供上傳端點，簽章網址作備援。
4. 任務要提前派送、有遲到上限；中樞短暫停機也照發；貼文網址延遲出現時先對帳，不自動重發。
5. 需要人處理的事件要能送到主人手上（指名機器與帳號），不只出現在遠端機器的桌面。
6. 舊工具在替代工具通過同一個真實模型測試前不移除；/w 在功能搬到 /app 前不隱藏。
7. 先做最小閉環，再做大規模刪除，避免又是一段時間什麼都不能用。
8. 每個完成標準都要能重測：固定用戶端與模型版本、重跑 5 次至少 4 次成功，並涵蓋失敗情境（機器離線、中樞重啟、上傳中斷、驗證碼、結果不明）。
