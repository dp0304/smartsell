# 数据采集与核对

## 自己的社媒账号状态与近期作品

For “查我的社媒状态” and “我的 X 账号现有视频”, use only the authorized SmartSell MCP and the user's own paired Worker. Check the live schemas for `worker_social_status_request` and `worker_social_status_get`.

1. Queue `worker_social_status_request` with a fresh high-entropy random `idempotency_key` (such as a UUID v4) for each new user query, even for the same brand and day. You may use local `uuidgen` solely to generate the ID, without network access. Never derive the key from a brand, date, or fixed sequence. Reuse the exact key and arguments only for a network retry of the same submission. In `body`, use `mode: "account_status"` for account or login state and `mode: "recent_posts"` with `platform: "x"` for existing X videos or recent posts. Recent posts currently support X only. For account status, set `platform` when specified. Omit `device_id` when the user has exactly one eligible paired Worker. If multiple Workers match, resolve the intended device from authorized context or ask for it. Include `expected_identity` only when the requested identity is known. Use the handle for X.
2. Poll `worker_social_status_get` with `params: { id: TASK_ID }` for the same task. Report the task ID, device ID, observed state for each platform and the Worker receipt time (`reported_at`). For an X video query, return links only for posts with `has_video: true`. Label a task from an earlier query, including a replay of that task, as a historical receipt with its original observation time. If still queued or claimed, report that state and the absence of an observation. If blocked, report the exact code and reason, such as unavailable tools or permissions, no paired Worker, a device offline, login or verification required, identity mismatch, expiry, or unsupported collection. Tell the user which Worker needs attention when applicable. Any requested sign-in belongs in visible Chrome on that Worker.
3. Keep the live check on the Worker. Do not fall back to external tools, the main Agent's local browser, web search, shell, curl, proxies or scraping. Label any stored posts or metrics as cached workspace data, with their original time and coverage when available. Missing or partial observations cannot establish a count of zero or prove an item is absent. For a specific existing SmartSell schedule, use the publishing target and its linked receipt to establish publication. A recent-posts observation establishes only what that Worker saw.

## 其他采集任务

Codex or Claude drives the work in the requested workspace's connected SmartSell MCP. Inspect the live tool list and schemas or use `smartsell_operations_describe`. Prefer named tools. Use `smartsell_operation_call` only for operations the current credential is allowed to call and the live catalog describes. Resolve the requested source or subject, account/store, time window and any Worker from authorized reads and context before asking for missing details. Never substitute a different workspace, account, store or device. A workspace-only read needs no Chrome check.

1. **Read or collect as requested.** For existing data, use the exposed reads for the requested subject: `data_source_list` / `data_source_get` and `data_source_coverage` for source policy and windows, `observations_list` for a watch target, `research_search` / `research_item_evidence` for research observations, or `metrics_query` for stored metrics. If asked to collect fresh data, first match the source's authorization, allowed resource, account/store and any configured executor. Where `sync_refresh` and `sync_run_get` are available, queue a supported read-only fetch for `params: { id: SOURCE_ID }` and the allowed `body.resource` using the live schema. `sync_refresh` uses the source's configured window. For an explicit historical reconciliation window, use `sync_reconcile` with the supported `resource`, `from` and `to` fields. Use an `idempotency_key` and read `sync_run_get` by the returned run ID. Check progress, errors and coverage, then read the relevant observations or metrics for the actual subject and window. Distinguish existing observations from what this run confirmed.
2. **Use Worker collection when supported.** Zhihu is one read-only route. When `zhihu_stats_create` and `zhihu_stats_get` are authorized, locate the user's active paired Worker via exposed device reads or existing authorized context. For the user's own profile queue `body: { device_id, profile_slug }`, or use `body: { device_id, mode: "login_check" }` for a requested login check only. Include an `idempotency_key` and read `zhihu_stats_get` with `params: { id: TASK_ID }`. Verify the returned device and profile against the request. Only a completed identity-checked stats result establishes the visible count text. For other platforms, use a read-only task only when live discovery exposes both the supported action and its readback. Respect the configured device and any current verified account/store identity evidence. A linked account or open page alone does not prove who is signed in.
3. **Record supplied observations only on explicit confirmation.** If authorized, use `analytics_record_observations` with its live schema, the user's permitted source, observation timestamps, requested metrics and a separate idempotency key. Report what the service accepted and read it back when exposed. Preserve the supplied provenance and never describe it as a fresh platform fetch.
4. **Report evidence and blockers.** Follow the same task, run or request ID through readback. Report source, scope, timestamps, status, coverage and warnings. Distinguish pending or partial results, `no_permission`, missing observations and measured zero. Reuse a key only for an identical retry. On `login_required`, ask the user to sign in in visible Chrome on the specified Worker and give the actual incident context (Web → Agent → Zhihu Worker incidents for Zhihu). Report identity mismatch, expired tasks, missing tools or access as they occur. Ask the user only for unresolved scope, necessary authorization, login or an existing human review. Do not requeue automatically when blocked, request credentials, bypass platform limits or ask the user to claim tasks, copy session IDs or run commands. If no supported collector is available, finish authorized reads and report the remaining collection gap.
